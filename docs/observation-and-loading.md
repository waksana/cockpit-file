# 消息观察、best effort 与卡片 loading

**当前实现。** delta best effort、文件库延期、不补捕获旧历史、
卡片单次自动 loading 最多五秒。本文描述代码契约，不把功能用例当成容量或性能认证。

## 1. 没人观看，不等于后端收不到原生消息

核对 Cockpit 基线
[`97f8e75`](https://github.com/waksana/cockpit/tree/97f8e75c65fbf18b9e3c85ca562c46d8db6f1990)
及所安装 SDK 1.0.13，现有两条链路不同：

| 链路 | 无人观看时 |
| --- | --- |
| Copilot runtime 到 SDK 的 session.event 通知 | 本宿主已加载会话的注册回调仍接收通知，不以浏览器是否打开为前提 |
| 浏览器驱动的聊天 eventLog.read / HTTP 流 | 页面不可见或不再查看该 session 时取消，不为显示而持续拉取 |

源码依据：

- `packages/core/src/runtime.ts` 的 sessionOptions 已开启 streaming 与 includeSubAgentStreamingEvents。
- `packages/core/src/engine.ts` 的 ensureLoaded 配置带所有权保护的 onEvent。
- SDK 的 client 处理 session.event 通知，将事件交给已存在的 session 回调。
- engine.onLive 当前主要使用控制事件，许多正文 delta 不进入控制处理。
- `apps/web/src/net/store.ts` 按 activeId 和页面可见性启动/取消聊天读取。

文件模块应当复用第一条链路，在宿主所有权检查之后获得只读通知，
不为了文件再开一套长期 eventLog.read，更不加载其他会话或延长原生 idle timeout。
控制状态本来需要的原生查询与聊天历史拉取是不同用途，不能一概称为“无人观看零 RPC”。

首版只处理模块实际启用后的新实时消息，不监听历史读页来补上传。
模块关闭时产生、安装前存在或后来恢复时重放的旧消息，都不因为用户翻阅而被捕获。
历史卡片仍按同一 URL 算法尝试读取：有已有快照就显示，没有就失败。
来源无法确认时不自动补抓，不以浏览器第一次渲染或宿主当前时间代替消息来源。

## 2. 新增负担是什么

模块增加的是增量正文识别、短期当前消息缓冲、每引用去重，以及真正匹配文件后的磁盘复制。
它不必额外调用模型，也不需要增加第二路原生聊天拉取。

不能说零成本：

- 不对每个 token 重跑完整历史 Markdown；在当前消息中增量/合批处理。
- 识别状态只保留当前需要的消息片段，结束/卸载后释放，不是聊天历史库。
- 同消息同引用只启动一个捕获操作。
- 没有文件引用的消息不读取磁盘文件。
- 文件复制使用非阻塞 I/O 和有界并发，不在同步 SDK 回调中完成。
- 模块 disabled 时没有解析和复制工作；已发生的 SDK 通知接收仍属本体原有运行模型。
- 不能为了追求漏零条而扫描全历史、保活 session 或无限积压任务。

实际 CPU、内存和磁盘成本须用合成持续输出、多会话和大文件场景量测，
不能仅凭“复用通知”就宣称没有运行负担。

## 3. delta best effort

delta 是任意文本片段，不保证 Markdown 边界。一个链接可能被拆成：

```text
片段 1：![效果
片段 2：图](./ab
片段 3：c.png
片段 4：)
```

前几个片段不够确定引用，片段 4 才使这个例子形成可识别的行内图片。
不能分别对每个 delta 执行完整链接正则，也不应每次从头解析累计正文。

### 增量快速路径

为正在输出的每条消息维护短期识别状态：

```text
稳定原生消息身份
已扫描位置
当前语法状态（正文、代码、转义、候选链接等）
尚未闭合的候选片段
已识别引用表（pending / ready / failed）
```

识别器对外提供 `feed(delta)`、`finish()`、统计和有界诊断，状态由所属消息隔离。
不必保存全部累计正文；保留当前语法状态、未闭合候选和必要去重信息即可。
JavaScript RegExp 的 lastIndex 不是跨 delta 的语法状态，不能直接代替这个识别器。

优先为常见 Markdown 行内文件链接和图片提供单向扫描快速路径：

```text
feed(delta)
  -> 只继续扫描新字符，保留跨片段状态
  -> 遇到可识别的完整候选，提取目标
  -> 候选已经见过：不重复规范化、查盘或提交捕获
  -> 新候选：规范化并校验模块支持的目标
  -> 规范目标已经处理：绑定到已有结果
  -> 否则先登记 pending，再提交异步复制
```

必须先登记 pending 再进行异步 I/O，防止接下来的 delta 或并发回调又提交一次。
同一文本中再次出现相同链接，扫描器仍需读取新字符和查表才能知道它重复，
但不重新执行链接语义处理或复制。不能承诺对重复文本连字符都无需读取。

已扫描前缀不会随每个 delta 从头分析；候选尾部增量追加，不每次复制/匹配整个长字符串。
同时处理代码围栏、行内代码、转义、链接目标中的括号等必要边界，
不能把代码示例中的文件链接当作真实交付。
快速路径以预期近线性文本扫描为目标，而不是随 delta 数量反复扫描不断增长的正文。

### 新消息完整事件补漏

完整事件属于同一条新实时消息，不是翻历史补上传：

- 与已有增量内容一致时，不重新分析已处理链接；只处理尚未扫描的尾部。
- 断流或内容修正导致不能确认一致时，可以对这条新消息做一次完整解析补漏。
  已识别引用仍通过同一表跳过语义处理/复制，不为“补漏”覆盖成功快照。
- 当前补漏仍使用同一识别器，覆盖其支持的行内链接/图片；
  引用式定义等复杂 Markdown 暂不自动捕获，不为了完整语法自建庞大解析器。
- 这意味着通常路径不重扫，修正路径可能有一次重扫；不能假称任意 Markdown
  和任意断流下都同时保证从不重扫、绝不误判、最早发现。
- 识别器的统计和分片用例用于约束扫描次数；它们不证明任意真实负载下的 CPU 或内存容量。

确认完整事件与已见增量是否一致，可以使用累计长度/摘要并对完整输入作一次校验，
不能仅凭长度相同判断，也不必为此永久保存累计正文。
这类一次性校验仍会读取字符，但不等于再次解析所有已识别链接。
正常扫描的目标是总文本近 O(N)、每字符常数级工作，而不是整条消息 O(1)。
内存由活跃消息数、候选长度和去重状态决定；必须有限额，不能宣称任意输入下恒定内存。

前端同样使用当前已可识别的 Markdown 节点立即渲染，不等待完整正文。
原生 delta 的 event.id 是片段身份，不是稳定消息身份。
目标被继续输入改写时，只处理新的引用，旧请求晚结果不能挂到新的节点上。
新消息结束/卸载后释放不再需要的扫描状态，持久文件绑定仍由模块保存，
用于后续读取和去重，而不是保存整份原生正文。

文件还不存在、正在生成或复制失败时不能声称 ready；
成功快照的定义为首次成功捕获的字节，而不是整条最终回复发出瞬间的字节。
临时引用后来消失、delta 中断和未捕获的旧文件版本都属于 best-effort 限制。

## 4. loading 如何转为 ready

只给 `<img src="...">` 返回一次错误并不够：
浏览器不会因为后端后来完成复制，就自动重新请求同一图片。
媒体元素也不会替应用执行 HTTP Retry-After 的业务重试。

当前采用**模块内部、按 URL 合并的 HEAD 可用性探测**，而不是额外消息协议：

```text
识别引用 -> FileCard loading
  -> HEAD 检查文件 URL
  -> 仍在准备：按服务端提示/退避稍后检查
  -> ready：显示元数据并提供下载；仅用户点击预览时加载图片/音视频原 URL
  -> 明确失败或达到五秒总预算：错误反馈和手动重试
```

这不是新增宿主展示资源图或每卡片 SSE。
200 表示可以读取，202 为已知进行中；404 可能是尚未登记或未维护的旧引用，
也只在原五秒预算内重试。422、授权失败及服务错误提前失败。
五秒是总预算，不是每个请求各等五秒；不存在不能无限等待。

共同要求：

- 同 URL 的在途检查可合并；卡片隐藏/卸载时停止其检查，无需常驻全局文件轮询。
- pending/暂时未就绪响应不能被长期缓存，否则 ready 后仍看到旧错误。
- 确认 ready 后不继续轮询；视频/大文件按原 URL 和 Range 读取，不整份 fetch 成 blob。
- 不通过探测或 GET 触发任意本地路径导入；捕获来自真实原生消息。
- 前端重试的是资源读取，不是重新发送 prompt 或重新创建文件版本。
- 首次进入 loading 时记录截止时间；重绘、后续 delta 和自动重试不延后截止时间。
- 最晚到五秒结束本轮 loading，取消本轮检查，显示失败/超时；明确错误可更早失败。
  后台标签页计时器被暂停时，恢复后先检查原截止时间，不能再获得完整五秒预算。
- 显式点击重试可以开始新一轮读取，但不会请求捕获旧文件；
  相同消息/URL的可见卡片在本次页面阅读期间不因组件重挂载自动无限开新轮询。
- HEAD 成功后停止该轮计时，不依赖未打开的媒体发出 load/metadata 事件。
  每次显式打开或重试媒体预览时启动独立的五秒加载期限，重绘不延期；
  关闭/卸载/换资源时释放该次等待。媒体失败不撤销原件 ready 状态。
  这不是用户上传、大文件完整下载或视频播放的全局超时。
- HEAD 超时或网络失败只表示尚未确认可用性，错误分类与完整原因分别保留。
  显示层不能通过英文错误文本匹配来猜测错误类别。
- 本次不改变隐藏页面的 HEAD 截止时间，也不解决 HTTP/1.1 多标签页长连接占满：
  浏览器尚未发出的排队请求也可能耗尽五秒。不得宣称紧凑展示消除了该间歇性失败。
- 卡片超时不自动取消其他消费者共享的后端捕获；后端工作需要自己的有界资源管理。
- 等待文件不阻塞正文流，也不延长宿主 graceful。
